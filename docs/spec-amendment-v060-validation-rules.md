# Smart Booking 機能追加仕様書（カスタムフィールドの入力ルール）

## ドキュメント情報

| 項目 | 内容 |
|------|------|
| 対象バージョン | v0.6.0 |
| ステータス | 仕様確定（2026-09-25 合意） |
| 背景 | 「MW WP Form のように、フィールドごとに細かなバリデーションルールを設定したい」という要望 |
| 前提 | v0.5.6 リリース済み。現状調査（2026-09-25）で、ルール保存先の不在・フロント検証の二重実装を確認済み |
| 設計原則 | YAGNI / シンプルさ優先 / 3原則（壊さない・デグレさせない・影響範囲を調査する） |

## 概要

フォーム設定のカスタムフィールドに「入力ルール」を設定できるようにする。採用するルールは次の3系統のみ。

1. **文字種**（単一選択）
2. **文字数の範囲**（最小〜最大）
3. **一致する項目**（メールアドレス確認欄など）

**最重要原則: ルール未設定（NULL）のフィールドは、フロント・サーバとも v0.5.6 と1文字も変わらない挙動とする。** アップデートしただけで検証が増えることはない。

---

## 1. 適用範囲

| 項目 | 仕様 |
|------|------|
| 文字種・文字数を設定できる型 | `text` / `textarea` |
| 一致ルールを設定できる型 | `text` / `email` / `tel`（比較先も同じ3型から選ぶ） |
| システム3項目（customer_name / customer_email / customer_phone） | ルールは設定不可。**一致ルールの比較先としてのみ選択可**（「メールアドレス（確認用）」を実現するため） |
| address / select / radio / checkbox | 対象外 |
| 適用する経路 | 公開予約（`POST /public/reservations`）とフロント予約フォームのみ |
| 適用しない経路 | 手動予約（`POST /admin/reservations`）、既存予約の編集（`PUT /admin/reservations/{id}`） |

### 評価をスキップする条件（意図しない検証の防止）

以下のいずれかに当てはまる場合、そのフィールドのルールは評価しない。

| 条件 | 理由 |
|------|------|
| ルールが NULL | 既存挙動の維持 |
| フィールドが条件フィールドで非表示 | 既存の「表示中のみ検証」原則に従う |
| 値が空欄（整形後） | 空欄の扱いは is_required の担当。任意項目は空欄で通る |
| **現在の field_type がルールの対象型でない** | text でルール設定後に select へ型変更した場合など、DB に残ったルールを無視する。保存時に消去するのではなく、評価側でガードする |
| 一致ルールの比較先が非表示 | 比較先が条件フィールドで非表示なら一致判定をしない |
| 一致ルールの比較先が存在しない | 防御的にスキップ（通常は §5 の削除ガードで発生しない） |

---

## 2. 評価手順（フロント・サーバ共通）

フィールドごとに次の順で評価し、**最初に失敗したもの1つ**をそのフィールドのエラーとする。

1. 可視判定（非表示ならスキップ）
2. 整形（§3）
3. 空欄判定 → 空欄なら is_required の既存判定のみ行い、ルール評価はしない
4. 文字種
5. 文字数
6. 一致

---

## 3. 値の整形

**整形はルールが設定されているフィールドにのみ適用する。** ルールなしのフィールドの値は従来どおり一切変更しない。

| 整形 | 内容 | 適用範囲 |
|------|------|---------|
| 前後の空白除去 | 先頭・末尾の半角空白、タブ、改行、全角空白（U+3000）を除去。PHP の `trim()` は U+3000 を除去しないため、正規表現 `/^[\s\x{3000}]+\|[\s\x{3000}]+$/u` で明示的に除去する | ルールありの全フィールド |
| 改行の統一 | `\r\n` と `\r` を `\n` に統一してから文字数を数える | 文字数ルール |
| 全角英数字の半角化 | U+FF10–FF19（０–９）、U+FF21–FF3A（Ａ–Ｚ）、U+FF41–FF5A（ａ–ｚ）を、コードポイントから 0xFEE0 を引いて半角に変換。**記号・空白は変換しない** | 文字種が「半角数字」「半角英字」「半角英数字」のフィールドのみ |

- 整形後の値で検証し、**整形後の値を保存する**。確認画面には整形後の値を表示する（ユーザーが変換結果を確認できる）
- 半角カナから全角カナへの変換は行わない（濁点の結合処理が必要で複雑になるため）。半角カナはエラーとする

---

## 4. ルール詳細

### 4-1. 文字種

| 値（JSON） | 表示名 | 許可文字（正規表現） |
|-----------|-------|---------------------|
| `numeric` | 半角数字 | `^[0-9]+$` |
| `alpha` | 半角英字 | `^[A-Za-z]+$` |
| `alnum` | 半角英数字 | `^[A-Za-z0-9]+$` |
| `katakana` | カタカナ | `^[\x{30A1}-\x{30F6}\x{30FC}\x{30FB}\x{30FD}\x{30FE}\x{3000} ]+$` |
| `hiragana` | ひらがな | `^[\x{3041}-\x{3096}\x{309D}\x{309E}\x{30FC}\x{30FB}\x{3000} ]+$` |
| `kana` | ひらがな または カタカナ | 上記2つの和集合（1つの値の中で混在可） |

- カタカナの範囲 U+30A1–30F6 には「ヴ」「ヵ」「ヶ」を含む。ひらがなの範囲 U+3041–3096 には「ゔ」を含む
- カナ系は長音「ー」、中黒「・」（「ジョン・スミス」等）、踊り字「ヽヾ／ゝゞ」、空白（全角・半角）を許可する
- 半角系3種は空白を許可しない（会員番号・コード等の用途を想定）。管理画面の説明文で明示する
- PHP は `u` 修飾子、JS はリテラルを `\u` 表記に置き換えて実装する（すべて BMP 内の文字のため JS の `u` フラグは必須ではないが、付与してよい）

### 4-2. 文字数の範囲

| 項目 | 仕様 |
|------|------|
| 設定 | 最小・最大の整数。片方だけの設定も可 |
| 入力範囲 | 1〜9999。空欄 = 未設定 |
| 保存時の検証 | 最小 > 最大の場合は保存を拒否（管理画面・サーバの両方） |
| 数え方 | PHP `mb_strlen($v, 'UTF-8')`、JS `[...v].length`（コードポイント数。絵文字等のサロゲートペアで両者の判定がずれるのを防ぐ） |
| 数える対象 | 整形後（§3）の値 |

「最小文字数」を独立項目にはしない（範囲の最大を空欄にすれば表現できる）。

### 4-3. 一致する項目

| 項目 | 仕様 |
|------|------|
| 設定 | 同一フォーム内の比較先フィールドを1つ選択（field_key で保持） |
| 比較先の候補 | 同一 form_id 内の text / email / tel 型フィールド（システム3項目を含む）。自分自身は除外 |
| 比較方法 | 双方を前後空白除去（§3）したうえでの完全一致。大文字・小文字は区別する |
| 比較先が空欄で自分が入力済み | 不一致エラー |
| 連鎖・相互参照 | 制限しない（すべて単純な文字列比較のため壊れない） |

---

## 5. 比較先の削除ガード

| 項目 | 仕様 |
|------|------|
| 対象操作 | 一致ルールの比較先になっているフィールドの**削除** |
| 挙動 | 削除を拒否し、依存しているフィールド名を提示する（v0.5.4 の親フィールドガードと同じ方式） |
| エラーコード | `smb_field_match_referenced`（HTTP 409 または既存の親ガードと同じステータスに揃える） |
| field_key の変更 | 変更可能な実装であれば、比較先になっている間は変更を拒否する（実装時に field_key の編集可否を確認し、編集不可なら対応不要） |
| 型変更 | 制限しない（文字列比較は型に依存しないため） |

---

## 6. データ設計

| 項目 | 仕様 |
|------|------|
| 追加カラム | `smart_booking_custom_fields.validation_rules` LONGTEXT NULL |
| NULL の意味 | ルールなし（既存全行は NULL のまま） |
| field_options への相乗り | 不採用（既に「選択肢」と「address の autofill 設定」で意味が二重化しているため） |
| マイグレーション | v0.6.0 ゲート（SMART_BOOKING_VERSION 基準・冪等）で dbDelta によるカラム追加＋ smart_booking_db_version の更新のみ。既存データの変換なし |
| uninstall | テーブルごと削除されるため追加対応不要（実装時に確認） |

### JSON 構造

```json
{
  "charset": "katakana",
  "min_length": 2,
  "max_length": 50,
  "match_field_key": null
}
```

- 各キーは省略可・null 可。すべて未設定なら NULL として保存する（空オブジェクトを保存しない）
- `charset`: `numeric` / `alpha` / `alnum` / `katakana` / `hiragana` / `kana` / null
- 未知のキーは保存時に破棄する
- 保存時（管理 API）に不正値（未知の charset、範囲外の数値、最小 > 最大、存在しない match_field_key、自分自身の参照、対象外の型への設定）は 400 で拒否する
- 実行時（予約送信時）に DB 上の値が不正だった場合は、そのルールを無視する（予約を止めない）

## 7. REST API

### 管理

| エンドポイント | 変更 |
|---------------|------|
| `POST /admin/custom-fields`、`PUT /admin/custom-fields/{id}` | `validation_rules` を受け付ける（§6 の検証を行う） |
| `GET /admin/custom-fields` | `validation_rules` を出力に追加 |
| `DELETE /admin/custom-fields/{id}` | §5 の削除ガードを追加 |

### 公開

| エンドポイント | 変更 |
|---------------|------|
| `GET /public/form-fields` | 各フィールドに `validation_rules` を追加（キー追加のみ。既存キーは変更しない） |
| `POST /public/reservations` | §2 の手順でルールを評価。エラーの返し方は現状どおり「最初の1件を code + message で返す」形式を維持 |

### 予約送信時のエラーコード（HTTP 400）

| コード | メッセージ例 |
|--------|-------------|
| `smb_reservation_field_format` | 「{ラベル}はカタカナで入力してください。」 |
| `smb_reservation_field_length` | 最小のみ「{ラベル}は{min}文字以上で入力してください。」／最大のみ「{ラベル}は{max}文字以内で入力してください。」／両方「{ラベル}は{min}〜{max}文字で入力してください。」 |
| `smb_reservation_field_mismatch` | 「{ラベル}が{比較先ラベル}と一致しません。」 |

フロントのインライン文言は、既存のインラインエラーの書式（ラベルを含めるか否か等）に合わせる。

## 8. フロント（予約フォーム）

| 項目 | 仕様 |
|------|------|
| 検証ロジック | 共有モジュール（`src/frontend/utils/validation.js` を想定）に一本化し、FormInput / MainInputPage の両方から利用する |
| 発火タイミング | 現状どおり確認ボタン押下時のみ。入力時・blur では検証しない |
| エラー表示 | 既存の a11y 実装（role="alert"、aria-invalid、aria-describedby、最初のエラー欄へのフォーカス）をそのまま使う |
| 整形の反映 | 整形後の値を state に反映し、確認画面・送信ペイロードにその値を使う |
| 利用者の入力中に管理者がルールを変更した場合 | フロントを通過してもサーバで弾かれうるが、サーバエラーは既存の仕組みで表示されるため許容する |

### 前提作業: フロント検証の一本化

`FormInput.validateField`（文言を返す）と `MainInputPage.isFieldValid`（真偽を返す）は同じロジックの別コピーになっている。新ルールを追加する前に共有モジュールへ一本化する。

- **一本化の前に、両者の判定差分を洗い出して報告する。差分があれば人間の判断を経てから統合する**（一本化そのものが意図しない検証の変化を生みうる唯一の工程のため）
- 一本化後、既存 E2E がすべて通ることを確認してからルール追加に進む

## 9. 管理画面（フォーム設定 > フィールド編集モーダル）

| 項目 | 仕様 |
|------|------|
| セクション名 | 「入力ルール」 |
| 表示条件 | 対象型（§1）のときのみ表示。システム3項目では表示しない |
| 文字種 | セレクト（指定なし / 半角数字 / 半角英字 / 半角英数字 / カタカナ / ひらがな / ひらがな または カタカナ）。text / textarea のみ |
| 文字種の説明文 | 半角系:「全角で入力された英数字は自動で半角に変換されます。空白は使えません」／カナ系:「長音（ー）・中黒（・）・空白を含めて入力できます」 |
| 文字数 | 最小 [ ] 〜 最大 [ ] の数値入力。text / textarea のみ |
| 一致する項目 | セレクト（指定なし + 候補フィールド）。text / email / tel |
| 型を対象外に変更したとき | セクションを非表示にする。保存済みのルールは消去しない（評価側で無視される） |

## 10. 変更しないもの

- CSV 出力、メール通知、予約一覧、予約詳細
- 手動予約の検証
- 既存のエラーコード・文言・a11y 属性
- field_type の種類（新しい型は追加しない）

## 11. 完了条件

- **全フィールドがルール未設定のとき、フロント・サーバの挙動が v0.5.6 と完全に同一**（デグレ最重要。既存 E2E が全件パス）
- フロント検証の一本化前に差分報告が行われている
- 各ルールがフロントと REST 直叩きの両方で同じ判定をする（付録 A のテストベクトルで検証）
- 全角英数字が半角ルールで自動変換され、確認画面・保存値に変換後の値が使われる
- 非表示の条件フィールド、空欄の任意項目、対象外の型に変更したフィールドでルールが評価されない
- 一致ルールの比較先の削除がブロックされ、依存フィールド名が提示される
- 管理 API が不正なルール（最小 > 最大、自分自身への参照など）を拒否する
- 手動予約でルールが評価されない
- v0.5.6 → v0.6.0 のマイグレーションが冪等に完了する

## 12. 不採用・保留事項（判断記録）

| 項目 | 判定 | 理由 |
|------|------|------|
| 文字種の複数選択（チェックボックス） | ❌ 不採用 | 「半角数字＋カタカナ」など入力不可能な組み合わせが作れてしまう |
| メールアドレス・電話番号・郵便番号ルール | ❌ 不採用 | field_type（email / tel / address）が担う。二重定義を避ける |
| 必須（チェックボックス）ルール | ❌ 不採用 | checkbox 型の is_required で実現済み |
| 最小文字数の独立項目 | ❌ 不採用 | 文字数範囲の片側指定で表現できる |
| URL・日付・日付（年月） | 🔵 保留 | 実要望なし。日付は形式チェックではなく日付ピッカー付きの型として検討すべき |
| 一致ルールのネスト禁止 | ❌ 不採用 | 単純な文字列比較のため連鎖しても壊れない。制約だけが増える |
| 一致ルール比較先の型変更ブロック | ❌ 不採用 | 文字列比較は型に依存しない |
| 半角カナ → 全角カナの自動変換 | ❌ 不採用 | 濁点結合の処理が複雑。スマホではほぼ発生しない |
| 手動予約へのルール適用 | ❌ 不採用 | 電話受付では情報が揃わないのが普通。既存方針（手動予約はカスタムフィールドを検証しない）を明文化 |
| サーバの複数エラー同時返却 | ❌ 不採用 | 公開契約の拡張が必要。フロントは既にフィールド単位で表示できる |
| 型変更時のルール自動消去 | ❌ 不採用 | 評価側のガードで十分。誤操作でルールを失わない（メール上書きの「OFF でも保存」と同じ思想） |

### 本リリースに含めない既知の課題（2026-09-25 調査で起票）

サーバ側の電話番号形式・桁数の未検証、カスタム email / tel 型のサーバ未検証、選択肢外の値の未拒否などは、今まで通っていた入力が弾かれるようになる挙動変更を伴うため、本機能とは別リリースで扱う。

## 付録 A: テストベクトル

フロント（予約フォーム操作）と REST 直叩きの両方に同じ入力を流し、判定が一致することを確認する。「保存値」は OK の場合に保存されるべき値。

| ルール | 入力 | 判定 | 保存値 |
|--------|------|------|-------|
| numeric | `12345` | OK | `12345` |
| numeric | `１２３４５` | OK | `12345` |
| numeric | `123 45` | NG（format） | — |
| numeric | `123-45` | NG（format） | — |
| numeric | ` 123 `（前後に半角空白） | OK | `123` |
| alpha | `Ｔａｒｏ` | OK | `Taro` |
| alpha | `Taro Yamada` | NG（format） | — |
| alnum | `ＡＢ１２` | OK | `AB12` |
| katakana | `ヤマダ　タロウ` | OK | `ヤマダ　タロウ` |
| katakana | `ジョン・スミス` | OK | そのまま |
| katakana | `ヴァイオレット` | OK | そのまま |
| katakana | `ｶﾀｶﾅ`（半角カナ） | NG（format） | — |
| katakana | `やまだ` | NG（format） | — |
| hiragana | `やまだ たろう` | OK | そのまま |
| hiragana | `ゆーき` | OK | そのまま |
| kana | `ヤマダ たろう` | OK | そのまま |
| length min=2 max=5 | `あい` | OK | — |
| length min=2 max=5 | `あ` | NG（length） | — |
| length min=2 max=5 | `あいうえおか` | NG（length） | — |
| length max=3 | `😀😀😀` | OK（3文字） | — |
| length max=3 | textarea `a\r\nb`（3文字） | OK | — |
| match（→customer_email） | 同一値 | OK | — |
| match（→customer_email） | 末尾に空白付きの同一値 | OK | 空白除去後の値 |
| match（→customer_email） | 大文字小文字違い | NG（mismatch） | — |
| 任意項目 + numeric | 空欄 | OK（評価しない） | — |
| 非表示の条件フィールド + numeric | `abc` を入力後に非表示化 | OK（評価しない・値破棄） | — |
| text で numeric 設定後に select へ型変更 | 選択肢の値 | OK（ルール無視） | — |
