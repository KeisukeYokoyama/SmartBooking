# H4: 条件フィールドの親をチェックボックスに変更すると、子の回答がサイレントに破棄される

最終更新: 2026-09-11
重大度: 🔴 **高**（**ユーザーが入力した内容が消える実害**。予約自体は正常完了するため誰も気づけない）
状態: **✅ 解決済み・WordPress.org 公開済み（v0.5.4 / 2026-09-11 / SVN rev 3690665 / commit `03d5966`・タグ `v0.5.4`）。案3＋案1 を実装・回帰ゲート Green。**
発見元: サイト側（`~/dev/smart-booking-website`）作業中に発見。

## ✅ 修正内容（v0.5.4）

| # | 対象 | 変更 |
|---|---|---|
| 案3-a | `includes/rest/class-rest-custom-fields.php::update_item` | 自身が既に他フィールドの親で、かつ **`field_type` が実際に変わり** 新種別が radio/select 以外なら 400 `smb_field_parent_type_locked`。COUNT は種別が変わるときだけ実行する（毎回のクエリ増を避ける） |
| 案3-b | `src/admin/pages/formsettings/CustomFieldModal.jsx` | 既存の `isAlreadyParent` を種別セレクタの `disabled` に再利用し、理由を help で説明 |
| 案1 | `src/frontend/fieldConditions.js::isFieldVisible` | `Array.isArray( parentVal )` なら `false`（サーバー `condition_met()` と判定を一致させる） |

**「種別が実際に変わるときだけ」判定する理由**: 既に親が checkbox になっている壊れたサイトで、
ラベル修正などの通常の編集まで 400 で弾かれると直せなくなる。この条件なら
**checkbox 親 → radio/select への修復は常に許可**され、壊れ方を増やす変更だけが止まる。

**E2E**: `tests/e2e/v054-condition-parent-guard.spec.js`（5テスト × desktop/mobile = 10）。
(1) ガードが 400 を返す (2) radio→select とラベルのみの更新は通る（過剰でない）
(3) 子の条件を解除すれば種別変更できる (4) 管理UI のセレクタが disabled (5) checkbox 親の下で子が表示されない。
**修正前は (1)(4)(5) が Red、(2)(3) が Green**。修正後は 10/10 Green。

## 事象

1. `radio`（または `select`）のフィールドAを作り、フィールドBに「Aが『希望する』のとき表示」の表示条件を設定する。
2. あとから**フィールドAの種別を `checkbox` に変更**して保存する。→ **保存できてしまう。**
3. フロントで A の「希望する」にチェックを入れると、**Bが表示される**。ユーザーはBに入力する。
4. **確認画面にもBの回答が表示される。** ユーザーは入力が受理されたと確信して送信する。
5. 予約は **正常に完了する**（エラーなし・予約番号も発行される）。
6. しかし **Bの回答はDBに保存されていない。** 予約詳細・CSV エクスポート・通知メールのいずれにも現れない。

## 根本原因：フロントとサーバーで配列の扱いが食い違う

`checkbox` の値は**配列**（例 `['希望する']`）である。

### フロント側：配列を文字列化して比較 → 一致してしまう
`src/frontend/fieldConditions.js:27`〜`:38`
（※依頼時の参照 `src/frontend/utils/fieldConditions.js` は誤り。実際は `utils/` 無しの `src/frontend/fieldConditions.js`）

```js
const current = parentVal === undefined || parentVal === null ? '' : String( parentVal );
const expected = ... String( field.condition_value ) : '';
return current === expected;
```

`String( ['希望する'] )` → `'希望する'` なので **`===` が成立し、子が表示される**。

> 補足: チェックが**2つ以上**なら `String(['希望する','その他'])` → `'希望する,その他'` で不一致となり子は非表示。
> つまり**「1つだけチェックしたときにだけ表示される」**という、さらに気づきにくい挙動になっている。

### サーバー側：配列は問答無用で不成立
`includes/rest/class-rest-public.php:820`〜`:833`（`condition_met()`）

```php
if ( is_array( $parent_value ) ) {
    // 親は radio/select ＝単一文字列値のみを想定。配列は不成立扱い。
    return false;
}
```

この `condition_met()` は**2箇所**で使われ、両方が害をなす:

| 行 | 用途 | 配列のときに起きること |
|---|---|---|
| `:994` | 必須チェックのスキップ（「表示中のみ必須」） | **必須設定でもバリデーションを素通り**する。だから 400 で弾かれず予約が完了してしまう |
| `:1192` | meta 行の保存スキップ | **回答が保存されない**（`continue` で meta 行を作らない → 予約詳細・CSV は空欄） |

この2つが噛み合った結果、「弾かれもせず、保存もされない」＝**完全な無言のデータ消失**になっている。

## なぜ不正な状態を作れてしまうのか（invariant が片方向にしか守られていない）

「親は radio/select のみ」という不変条件は**子側からしか検証されていない**。

- ✅ **子→親の方向**: `includes/rest/class-rest-custom-fields.php:233` が
  `! in_array( $parent['field_type'], array( 'radio', 'select' ), true )` で弾く。
  管理UIも `CustomFieldModal.jsx:161` で親候補を radio/select に絞っている。
- ❌ **親自身を編集する方向**: `update_item` に **「自分が既に誰かの親なら種別を変えさせない」というガードが無い**。
  管理UIの種別セレクタ（`CustomFieldModal.jsx:327`）も、既に親であるフィールドに対して `disabled` にならない。

**つまり invariant は存在するのに、裏口が開いている。** これが本件の構造的な原因。

> なお `CustomFieldModal.jsx:189` に **`isAlreadyParent`（自分が既に他フィールドの親か）というフラグが既にある**。
> 現在はネスト禁止のために「表示条件セクションを出さない」用途（`:392`）にしか使われていないが、
> **種別セレクタの disabled にそのまま再利用できる。**

## 対応案の評価

### 案1: フロントをサーバーに合わせる（配列は不成立とする）
- **変更**: `fieldConditions.js` の `isFieldVisible()` に `Array.isArray( parentVal ) → return false` を追加（1〜3行）。
- **効果**: 子が**最初から表示されない**。ユーザーは入力しないので**消えるものが無くなる**。フロントとサーバーの判定が完全一致する。
- **副作用**: 設定した条件が黙って成立しなくなる＝「子フィールドが永久に出てこない」という別の分かりにくさは残る。ただし**データ消失よりは軽い**。
- **仕様書変更**: 不要（サーバーの既存挙動に合わせるだけ）。

### 案2: サーバーを配列許容にする（`in_array` で判定）（**非推奨**）
- **変更**: `condition_met()` の配列分岐を「`condition_value` が配列に含まれれば成立」に変更。
- **効果**: ユーザーの意図に最も近い（チェックしたら子が出て、保存もされる）。
- **非推奨の理由**:
  1. **公開契約と仕様の拡張になる。** 「親は radio/select のみ」は `docs/smart-booking-spec.md` と管理UI・REST 検証（`:233`）が揃って前提にしている設計。checkbox を親として正式サポートするなら、管理UIの親候補（`CustomFieldModal.jsx:161`）も checkbox を含めるよう変更が必要で、**仕様書の改訂＝凍結正本の変更＝人間承認**が要る。
  2. **複数チェック時の意味論が未定義。** 「『希望する』と『その他』の両方にチェック」で子を出すのか（OR）出さないのか（完全一致）を決める必要がある。フロントの現行実装は完全一致（`'希望する,その他' !== '希望する'`）で、`in_array` は OR。**どちらを正とするかは仕様判断**であり、バグ修正の裁量を超える。
  3. これは不具合修正ではなく**機能追加**（「チェックボックスを条件の親にできる」）。パッチリリースの看板で公開契約を広げることになる。

### 案3: 不正な状態を作れなくする（根本原因の封鎖）
- **変更**:
  - `includes/rest/class-rest-custom-fields.php::update_item`: 自分が既に親か
    （`SELECT COUNT(*) ... WHERE condition_field_key = <自身の field_key> AND form_id = %d`。
    **`:224` に同じクエリが既にある**ので流用できる）を確認し、親でありながら
    新しい `field_type` が radio/select でなければ 400（例 `smb_field_parent_type_locked`）。
  - `src/admin/pages/formsettings/CustomFieldModal.jsx`: `isAlreadyParent`（`:189`・**既存**）が true のとき
    種別セレクタ（`:327`）を `disabled` にし、「このフィールドは他のフィールドの表示条件に使われているため種別を変更できません」と help を出す。
- **効果**: **これ以上この壊れ方が発生しなくなる。** 既存の invariant を完成させるだけで、新しいルールを発明しない。
- **限界**: **すでに壊れている設定は救われない**（案3 だけでは、既に checkbox になっている親の下で消失が続く）。
- **仕様書変更**: 不要（既存の制約を実装で守るだけ）。

## 推奨: **案3（本命）＋ 案1（防御）**。案2 は採らない

**根拠**:
1. **案3 が根本原因**。invariant は既に存在し、REST の `:233` で片方向だけ実装されている。**裏口を塞ぐのが本筋**で、仕様書も公開契約も変えずに済む。既存の `isAlreadyParent` フラグと `:224` のクエリをそのまま再利用でき、実装コストも小さい。
2. **案1 を併せる理由は既存被害の停止**。案3 は将来の発生を防ぐだけで、**すでに親が checkbox になっているサイトでは今日もデータが消え続ける**。案1 を入れればフロントとサーバーの判定が一致し、「表示して入力させてから捨てる」という最悪の経路が即座に消える。2案あわせて「もう作れない・今あるものも害を出さない」が揃う。
3. **案2 を採らない理由**は上記のとおり、仕様・公開契約の拡張であり複数チェック時の意味論という未決の仕様判断を含むため。**欲しい機能ではあるので、別トラックの機能要望として扱うべき**（「チェックボックスを表示条件の親にする」）。

## ⚠️ 既に失われたデータは復旧できない

meta 行が**そもそも書かれていない**（`:1192` の `continue`）ため、過去に消えた回答はDBのどこにも存在せず**復旧不可能**。
修正リリースの Changelog には、**該当設定を使っていたサイトは過去の予約でその項目が空欄になっている可能性がある**旨を明記すべき。

## 検証時に必ず押さえる点（実装フェーズ向けメモ）

- 再現テスト（Red）: radio 親＋子を作る → 親を checkbox に変更 → フロントで1つだけチェック → 子に入力 →
  **確認画面に出ることを確認** → 送信 → **meta 行が無いこと**を assert。これが現在の壊れた挙動。
- 案3 適用後: 親の種別変更が 400 で弾かれること／管理UIでセレクタが disabled になること。
- 案1 適用後: 既に checkbox になっている親の下で、子が**表示されない**こと。
- 回帰: radio/select 親の正常系（`tests/e2e/v030-conditional-fields.spec.js` 想定）が無傷であること。
