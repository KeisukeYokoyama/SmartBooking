# H2: 管理者トグル OFF ＋ 店舗メール未設定で、担当者CC ごとサイレント抑止される

最終更新: 2026-09-10
重大度: 🟡 中（**管理者側通知のみ**。お客様宛の予約完了メールは影響を受けない）
状態: **調査完了・修正は GO 待ち**

## ⚠️ 前提の訂正

依頼時に「ADR または起票に記載済みの対応案3つ」とあったが、**その記録は存在しない**。
`docs/` 全文検索の結果、本件の対応案を記した ADR も起票も無く、
`docs/investigation/mail-recipients-20260806.md` の 案A / 案B は
**別論点（要望2＝管理者宛に複数アドレスを追加したい）** のものである。

## 事象

`includes/class-email.php:120`〜`:129`

```php
} else {
    // OFF: 店舗メールがなければ送らない（担当者だけのケースも送信しない）。
    if ( '' === $store_email || ! is_email( $store_email ) ) {
        return;                      // ← :123
    }
    $to_list[] = $store_email;
    if ( '' !== $staff_email && is_email( $staff_email ) ) {
        $cc_list[] = $staff_email;
    }
}
```

「管理者へのメール」トグルが **OFF** かつ **店舗メールが空/不正**のとき、
**担当者メールが設定されていても** `:123` で早期 return し、管理者系通知が一切送られない。

さらにこの return は `send()` に到達しないため、
v0.2.3 で導入した診断用 transient `smart_booking_last_mail_error` にも**記録されない**
（記録は `send()` 内の `record_error()` が担っている）。
＝管理画面の警告バナー（`MailSettingsTab.jsx` の `MailErrorBanner`）も**出ない**。**完全な無言**。

### 意図的な設計だった（記録あり）
`docs/bugs/v0.2.3-bug-ledger.md` が当時の分岐マトリクスに
「管理OFF×店舗無 → 管理者通知を無言 skip（`class-email.php:85`＝現 `:122-124`）」を挙げ、
可視化対応でも「**T3(:85) は対象外＝意図的無送信**」と明記している。
**見落としではなく、当時の判断。** ただし当時は「担当者CC も道連れになる」点と
「UI 文言が逆のことを言っている」点は検討されていない。

## 仕様書との関係（重要）

`docs/smart-booking-spec.md:583` は
「**管理者宛**: 店舗のメールアドレス。担当者メールが設定されている場合は**CCとして**送信」
と定義している。**担当者は CC 専用**であり、店舗メール（＝To）が無い状態は仕様が想定していない未定義領域。
＝現在の挙動は**仕様違反ではない**。仕様が沈黙している端に UI 文言だけが踏み込んでいる状態。

## 対応案の評価（実装コスト・副作用）

### 案A: UI 文言を実装に合わせる（推奨・その1）
- **変更**: 上表の3文言。＋ 仕様書 §8.2 に「トグル OFF 時、店舗メール未設定なら管理者系通知は送信されない」の1行追記。
- **コスト**: 小。JSX 3箇所 ＋ `npm run build`。新規テスト不要。
- **副作用**: **なし**（挙動不変・DB/option/REST 契約に一切触れない）。デグレリスクゼロ。
- **弱点**: 罠自体は残る。ユーザーが文言を読む必要がある。

### 案B: 店舗メールが無いとき担当者を To に昇格させる（**非推奨**）
- **変更**: `class-email.php` の OFF 分岐に5行程度。
- **コスト**: 中。OFF × 店舗有無 × 担当有無の4組合せ E2E が新規に必要（**現在 OFF 経路の E2E は1本も無い**。`v050-form-mail-overrides.spec.js:140` が `'1'`＝ON に設定しているだけ）。
- **副作用（採らない理由）**:
  1. **既存サイトの挙動が更新だけで変わる。** 「OFF ＋ 店舗メール無 ＋ 担当者メール有」の運用者は、**何も操作していないのに**アップデート後から通知が届き始める。全通知を止める意図で OFF にしていた場合は事故。v0.5.2 の「新店舗追加でデフォルト店舗がサイレント切替」と同じ**利用者の意図に反する黙示の変更**であり、3原則（現在のプログラムを壊さない／デグレを発生させない）に抵触する。
  2. **仕様書 §8.2「担当者は CC」から逸脱する。** 仕様書は凍結された正本であり、変更には人間承認が必要（CLAUDE.md）。
  3. メールヘッダ上、担当者が To/CC のどちらに出るかが状況で変わり、説明が難しくなる。

### 案C: 無言 skip を可視化する（推奨・その2）
- **変更**: `:123` の裸の `return` を `record_error( 'skipped_no_admin_recipient', ..., 'admin' ); return;` に置換
  ＋ `MailSettingsTab.jsx:45` の `MAIL_ERROR_CATEGORY_LABELS` に日本語1行追加。
- **コスト**: 小。PHP 1行 ＋ JSX 1行 ＋ `npm run build`。E2E は OFF 経路1本あれば十分。
- **既存機構の再利用**: v0.2.3 で「無言 skip を見えるようにする」ために作った transient + 警告バナーが**そのまま使える**。新機構を作らない（YAGNI 準拠）。`MailSettingsTab.jsx:83` に未知カテゴリのフォールバック文言があるため、**ラベル追加を忘れても壊れない**。
- **副作用**: 「担当者メールも未設定」＝**意図的に全通知を止めている**利用者にも毎予約バナーが出るとノイズになる。
  → **記録するのは「担当者メールが設定されているとき」だけにスコープする**ことで解消できる（＝利用者の期待が実際に裏切られている場合に限る）。

## 推奨: **案A ＋ 案C（スコープ付き）**。案B は採らない

**根拠**:
1. 依頼で問題視されたのは「**サイレント**抑止」であって「送られないこと」自体ではない。A＋C は**沈黙を除去する**（事前に文言で予告し、実際に発火したときはバナーで知らせる）。挙動は1バイトも変えないのでアップグレード事故が起きない。
2. 案B は仕様書の凍結領域（担当者＝CC）に踏み込み、かつ既存サイトの通知先を無操作で変える。**通知先の変更は利用者が明示的に決めるべき事柄**であり、更新の副作用として起こしてよい種類の変更ではない。
3. A＋C を出した上でなお「担当者だけに送りたい」需要が残るなら、それは**特別扱いではなく一般解**で解くべき。
   `docs/investigation/mail-recipients-20260806.md` §4 案A の追加宛先 option
   （`smart_booking_mail_admin_extra_recipients`）が「管理者系を誰に送るか」を正面から解決し、
   option 追加のみ＝非破壊・マイグレーション不要で、v0.5.1 の option 追加と同型。
