# 未対応: 撮影環境が回帰フィクスチャ（店舗1 / 担当者1）と DB を共有し、マニュアル画像に写り込む

最終更新: 2026-09-12
起票元: `docs/bugs/screenshot-seed-customer-name-label.md` の是正作業中に、
「撮影側を回帰テスト用フィクスチャから独立させられるか」を検討した結果。
重大度: 🔵 低（見た目のノイズ。プラグインの動作には無影響）。
トラック: **未着手。環境レベルの変更なので単独スコープ。**

## 事象

撮影は wp-env の DB を回帰スイートと共有している。回帰スイートのフィクスチャ
`店舗1` / `担当者1`（どちらも id=2）は撮影シードの管理外なので消えず、
**住所も電話も空のカードがマニュアル画像に写る**。

2026-09-12 の撮影で実測（`screenshot-text/` の grep ＋ 画像の目視）:

| カット | 写っているもの | 画像に見えるか |
|---|---|---|
| `stores/01-store-list.png` | `店舗1` のカード ＋ タブのバッジ `店舗 4` / `担当者 5` | **見える** |
| `stores/02-store-add-modal.png` | モーダル背後の `店舗1` カード ＋ バッジ `店舗 4` | **見える** |
| `staff/02-staff-add-modal.png` | バッジ `店舗 4` / `担当者 5` | バッジのみ見える |
| `forms/03-reservation-form-column.png` | 絞り込み `<select>` の選択肢 | 見えない（DOM のみ） |

＝ 実際の新規インストールなら店舗は 0 件のはずが、**デモ 3 件＋フィクスチャ 1 件で「4」と表示される**。

## 現状の対処と、その限界

撮影シードはデモ側の `sort_order` を 1/2/3、フィクスチャを 10 のままにして**下へ回している**
（`tests/screenshots/seed/README.md`「デモ店舗・デモ担当者の並び順」）。
順序は解決するが**消えるわけではない**ので、上表のとおり写る。

## 採らない案とその理由（2026-09-12 の判断）

**シードがフィクスチャ行を DELETE して purge で復元する方式は採らない。**

- このシードは「**レジストリ外の行は読むだけで変更しない**」を明文の契約にしている。
  他の持ち主の行を消すのはその契約の反転で、**ユーザーの実データが入った環境で走らせたときに破壊的**。
  撮影シードは開発用ツールだが、破壊的になりうる分岐を持たせたくない。
- 名前（`店舗1`）で狙い撃ちする実装は wp-env 固有のハックであり、フィクスチャ名が変われば黙って効かなくなる。
- `is_active=0` にしても一覧からは消えない（無効バッジ付きで表示される）ため回避にならない。

## 推奨する解（要判断）

**撮影セッションを「回帰フィクスチャの無い DB」で走らせる。**

1. **案A: 撮影専用の wp-env インスタンス**（`.wp-env.override.json` で別ポート・別ボリューム）。
   回帰スイートと完全に分離でき、共有 DB 由来の問題（本件・`お名前` の件の両方）が構造的に消える。
   コスト: Docker のリソースと起動手順が増える。
2. **案B: 撮影前に DB をリセットする手順を運用に足す**
   （`wp db reset` → プラグイン activate → seed）。コード変更ゼロ。
   コスト: 回帰スイートの DB スナップショット（`tests/e2e/.db-snapshot.json`）を撮り直すことになる
   （`global-setup.js` が自動再取得するので実害は小さいはず＝**未検証**）。

どちらも「撮影シードにフィクスチャを消させる」より筋が良い。**案B から試すのが低コスト。**

## 現時点の扱い

**既知の限界として `tests/screenshots/seed/README.md` に明記済み。**
サイト側のヘルプ原稿で店舗一覧のカットを説明するときは、`店舗1` が例示データでないことに触れないか、
この件が解決してから差し替えること。
