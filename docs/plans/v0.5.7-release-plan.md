## 2. 事象と根本原因（起票の要約・詳細は起票が正本）

`src/admin/pages/formsettings/FormMailTab.jsx`

- 共通テンプレートはマウント時の非同期取得で state に入る（`:85`〜`:99`、初期値 `{}`＝`:74`）。
- `handleToggle` は**クリック時点の `commonTemplates` を読むだけ**（`:121`〜`:141`、確定書き込みは `:134`〜`:135`）:

  ```js
  subject: commonTemplates[ meta.subjectKey ] || '',   // 未ロードなら '' が確定してしまう
  body:    commonTemplates[ meta.bodyKey ]    || '',
  ```

- プリセットは `hasDraft` 判定を通ったブロック内での**一度きり**。`commonTemplates` が後から到着しても
  再プリセットする経路が無い＝**一度空になると復元されない**。

実害の範囲（起票で確認済み）: 送信時は空 override を共通へフォールバックするためメールは壊れず、
REST が 400 で弾くため DB にも不正な状態は残らない。**実害は「空欄プリセット」と「原因不明の 400」**。

## 3. 推奨案 = **案2（到着時の遅延補完）**

| 案 | 内容 | 評価 |
|---|---|---|
| 案1 | 取得完了までトグルを `disabled` にする | 実装は最も単純だが、**タブを開いた直後に操作できない一瞬が生まれる**。速い環境では一瞬すぎて「なぜ押せないのか」が伝わらず、遅い環境では操作を奪う |
| **案2（推奨）** | `commonTemplates` 到着時の `useEffect` で、**`enabled` かつ subject/body が両方空の override だけ**をプリセットで埋める | トグルを塞がない。既存の `hasDraft`（下書きがあれば破棄しない）と**同じ判定条件**を再利用でき、仕様の一貫性が保てる。競合時も「空だったものだけ埋める」ので上書き事故が起きない |
| 案3 | `handleToggle` 内で `API.settings.get()` を await してからプリセット | クリックのたびに通信が走る。3種別を触ると最大3回。押してから反映までのラグも増える |

### 案2 の実装スケッチ（**未実装**。実装時に generator が確定させる）

```js
// FormMailTab.jsx — commonTemplates 到着後の遅延補完
useEffect( () => {
    if ( ! commonTemplates || Object.keys( commonTemplates ).length === 0 ) return;
    setOverrides( ( prev ) => {
        let touched = false;
        const next = { ...prev };
        MAIL_TYPES.forEach( ( type ) => {
            const o = prev[ type ];
            // 「ON かつ 件名・本文が両方空」＝ 未ロード中に ON されたものだけを対象にする
            // （hasDraft と同じ条件の裏返し。下書きがあるものには触れない）
            if ( o.enabled && ! o.subject && ! o.body ) {
                const meta = MAIL_TYPE_META[ type ];
                next[ type ] = {
                    enabled: true,
                    subject: commonTemplates[ meta.subjectKey ] || '',
                    body: commonTemplates[ meta.bodyKey ] || '',
                };
                touched = true;
            }
        } );
        return touched ? next : prev;
    } );
}, [ commonTemplates ] );
```

**設計上の注意（実装時に必ず守ること）**

1. **`initial` は書き換えない。** 遅延補完は「ユーザーが ON にした結果の続き」なので、
   `isDirty` は true のままであるべき（＝保存ボタンを押せる状態を維持する）。
2. **`prev` を返して no-op にする分岐を必ず持つ**（`touched` フラグ）。毎レンダーで新オブジェクトを
   返すと `isDirty` の再計算と `onDirtyChange` が無駄に走る。
3. **`enabled === false` の種別には触らない。** OFF の下書きを勝手に埋めると
   「OFF にしても破棄しない」既存仕様の意味が変わる。
4. **共通テンプレートが空文字のケースと未ロードを区別する。** `settings` が本当に空（未設定）なら
   補完しても空のままで正しい。`commonTemplates` が `{}`（未ロード）のときだけ待つ。
5. `API.settings.get()` の**失敗は握り潰す既存設計を維持**する（補助情報であり、タブ本体は動かす）。

## 4. 再現ファースト（Red テストの設計）

**現状のテストでは Red が安定しない。** `tests/e2e/v050-form-mail-tab.spec.js` の
`openMailTab()`（`:92`〜`:103`）は `window.smartBookingAdmin?.nonce` とトグルの出現しか待たず、
**設定取得の完了を待たずに即クリック**するため、速い環境では通ってしまう（起票の実測では
mobile 反復5回中4回失敗＝**タイミング依存**）。回帰ゲートの判定材料にはフレークを使わない。

### 設計方針: **`page.route()` でレスポンスを遅延させ、レースを決定論にする**

```js
// 例: tests/e2e/v057-form-mail-common-template-race.spec.js（新規・未作成）
let releaseSettings;                       // 応答を握るハンドル
await page.route( '**/smart-booking/v1/settings**', async ( route ) => {
    await new Promise( ( r ) => { releaseSettings = r; } );   // テストが許可するまで返さない
    await route.continue();
} );
```

1. **(1) 未ロード中に ON にしても空で確定しない**（本命の Red）
   - settings のレスポンスを保留したままメールタブを開く。
   - `#smb-form-mail-toggle-reception_user` を ON。→ 件名・本文は空になる（現状の挙動）。
   - `releaseSettings()` でレスポンスを解放。
   - **期待**: 件名 = 共通の件名、本文 = 共通の本文。
     **修正前は空のまま＝Red。修正後 Green。**
2. **(2) 下書きがあるときは上書きしない**（案2 のガード）
   - 先に override を保存してある種別（件名・本文入り）を OFF → ON する。
   - settings 解放後も**保存済みの下書きのまま**であること。
3. **(3) OFF の種別は補完されない**
   - 解放後、OFF の種別の `subject`/`body` が空のままであること（DB にも書かれないこと）。
4. **(4) 既存の正常系が壊れていない**（回帰）
   - 遅延なしでタブを開き、ON でその場でプリセットされる従来の挙動。
   - これは既存 `v050-form-mail-tab.spec.js` の A/B/C が担保しているので、**新規 spec では重複させない**。

> ⚠️ **テストだけを直して赤を消すのは症状の隠蔽**（起票の警告）。
> `openMailTab()` に待ち条件を足すのは**プロダクト修正が入った後**にする。
> 待ち条件を足すのは「テストを安定させるため」であって、レース自体は (1) の新規 spec が守る。
