# 絞り込み回帰ゲートの盲点 — 調査と改善案

- 作成日: 2026-09-12
- 種別: **調査と提案のみ**（実装なし・テストもコードも変更していない）
- きっかけ: `phase9-redesign-confirm-responsive.spec.js` が **v0.5.3〜v0.5.6 の 4 リリース**にわたって
  絞り込み対象に一度も入らず、赤 2 件がそのまま残り、さらに `mode: 'serial'` の巻き添えで
  **4 テストが did-not-run** になっていた（`docs/bugs/phase9-form-width-mobile-285px.md`）。
- 問い: **同種の「絞り込みから漏れ続けている spec」が他にもあるか。絞り込み方式をどう直すべきか。**

---

## 1. 現行方式と、その盲点の構造

現行の回帰ゲートは「**変更が触るコードから到達可能な spec だけを、変更前後で比較する**」方式
（`.claude/agents/logic-evaluator.md` ／ 各リリース計画書 §「絞り込みの根拠」）。

この方式が保証するのは **「今回の変更が新しい赤を増やしていないこと」だけ**である。
保証しないものが 2 つある。

1. **対象外の spec は 1 度も実行されない。** 赤があっても観測されない。
   変更と無関係な原因（環境ドリフト、共有 DB の状態、WP コア/テーマの更新、テスト自身の陳腐化）で
   赤くなった spec は、**誰かがたまたまその領域を触るまで発見されない**。
2. **「実行されたテスト数」を数えないと did-not-run が消える。**
   `mode: 'serial'` の describe は 1 件落ちると後続が丸ごと skipped になる。
   expected の件数だけ見ていると「前も 19、今も 19」で通ってしまう。

＝ **絞り込みは「変更の安全性」の道具であって、「スイート全体の健全性」の道具ではない。**
現在は後者を担う仕組みが**どこにも無い**。

## 2. 「一度も名前が出ていない spec」（文書ベースの下限）

`docs/handoff/state.md`（引き継ぎの正本）に **spec 名が 1 度も出てこない** spec を機械的に数えた。
本日のコミット前（`c61f94a`）時点。全 54 spec 中 **15 本**。

```
bug-a-plain-regate            phase4-chatwork          v040-fallback
bug124-scope-isolation        phase4-google-calendar   v040-schedule-sharing
phase2-pages-render           phase5-ux                v055-mail-admin-off-skip
phase2-reservations-smoke     phase8-ui-ux-fixes
phase2-schedule               phase9-redesign-picker
phase3-calendar               regression-gen-b-bugs
```

- これは**下限**である。名前が出ていても「ゲートで実行した」とは限らない
  （実際 `phase9-redesign-confirm-responsive` は 0 件ではなかったのに、ゲートには一度も入っていなかった）。
- 逆に **0 件なら確実にゲートに入っていない**。上の 15 本は少なくとも v0.5.3〜v0.5.6 の
  4 リリースで一度も回されていない。
- 内訳を見ると `bug124-scope-isolation`（**店舗×担当者スコープ隔離ゲート**の実体）、
  `phase2-schedule`、`phase3-calendar` など、**壊れたら重い領域**が含まれている。

## 3. 実測（フルスイート 1 回）

§2 は「記録に出ていない」だけなので、実際に赤があるかは別途の確認が要る。
そこで **`npx playwright test`（全 54 spec・736 テスト・desktop/mobile 2 プロジェクト）を 1 回**
流した。結果は本節に追記する。

> 実行時間の実測: 約 25 分で 97/736。単一ワーカー直列（`workers: 1`）＋ wp-env CLI 経由の
> DB 操作がテストごとに入るため、フルスイートは **数時間規模**。
> ＝ **開発ループで毎回回すのは非現実的**（案1 が「リリース前に 1 回」なのはこのため）。

## 4. 改善案（実装しない・採否は人間判断）

絞り込み自体は**やめない**。開発中の高速ループには必要で、根拠も毎回書かれている。
足りないのは「スイート全体の健全性を定期的に観測する仕組み」なので、そこだけ足す。

### 案1（最優先）: リリース前に**フルスイートを 1 回**回し、赤の一覧を記録する

- 絞り込み比較は今までどおり「変更の安全性」の判定に使う。
- そのうえで**リリース直前に 1 回だけ**フルスイートを流し、赤を全部列挙して state.md に残す。
  新しい赤があれば、スコープ内なら直す／スコープ外なら `docs/bugs/` に起票してから公開する。
- コスト: 2026-09-12 実測で **736 テスト**。バックグラウンド実行なら待ち時間は実質ゼロにできる。
- これだけで本件（4 リリース見逃し）は初回で捕まった。

### 案2: 既知の赤を**ファイルに置く**（prose をやめる）

現在「既存赤 4 件」は state.md の散文にある。機械照合できないので、
リリースごとに人間が読み比べるしかなく、**記録漏れがそのまま監視漏れになる**。

```
tests/e2e/known-reds.json   例: [{ "file": "...", "line": 327, "project": "mobile", "ticket": "docs/bugs/..." }]
```

- フルスイートの JSON レポートとこのファイルを突き合わせれば、
  「新規の赤」「直ったのに記録が残っている赤」の両方が自動で出る。
- **各エントリに起票リンクを必須にする**と、「起票なき既存赤」を作れなくなる。

### 案3: ゲートの判定条件に **did-not-run と総テスト数**を明示的に含める

- 現在の判定は「新規失敗ゼロ」。ここに
  **「テスト総数が減っていないこと」「did-not-run が増えていないこと」**を足す。
- 本件では baseline 26 テスト中 **4 件が did-not-run** だった。expected だけ見ると気づけない。
- v0.5.4 / v0.5.5 の記録には既に「did-not-run 0 / skipped 0 を確認」と書かれており、
  **運用としては始まっているが判定条件としては明文化されていない**。明文化する。

### 案4: 絞り込みの根拠に「**serial describe の巻き添え**」を必ず含める

- 変更が触るテストと同じ `mode: 'serial'` の describe に属するテストは、
  1 件落ちると後続が全部 did-not-run になる。
- ＝ **到達可能性だけで絞ると、同 describe の他テストの状態変化を見落とす。**
  絞り込み対象を決めたら「その spec が serial かどうか」を必ず確認し、serial なら
  **describe 単位で件数を突き合わせる**。

### 案5: 実行した spec 名を機械可読な形で残す

- state.md の散文ではなく、リリースごとに「このリリースで実行した spec 一覧」を
  リスト（1 行 1 spec）で残す。
- そうすれば「**N リリース連続で 1 度も実行されていない spec**」を機械的に出せる。
  §2 の調査が毎回 1 コマンドで済むようになる。

### 採らない案

- **毎回フルスイート**: 736 テストを開発ループのたびに回すのは現実的でない。
  絞り込みをやめる提案にはしない。
- **赤い spec を skip/削除して緑にする**: 赤の原因（テストの陳腐化 or 実装の不具合）を
  判定せずに消すのは、本件で見つかった「存在しない仕様をテストが固定していた」型の問題を
  隠すだけになる。**起票して残す**のが正しい。

## 5. まとめ

- 絞り込みは正しい道具だが、**スイート全体を見る目が無い**のが盲点。
- **案1（リリース前フルスイート 1 回）＋案2（既知の赤をファイル化）**で、本件の型の見逃しは塞げる。
- **案3・案4** は今回の did-not-run 4 件を捕まえるために必要。
- **案5** は「漏れ続けている spec」を毎回 1 コマンドで出せるようにする補助。
