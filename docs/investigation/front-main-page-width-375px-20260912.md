## 1. 結論サマリ（事実として確定したこと）

1. **375px で `.smb-front-main-page` が 285px になるのは、計算どおりの正しい結果**。
   内訳は `375 −（テーマの左右パディング 30+30）−（プラグインの左右パディング 15+15）= 285`。
   どこにも「想定外の余白」は無い（実測・§2）。
2. **テストが期待する 327px（`100vw − 48px`）は、テーマの余白を勘定に入れていない値**。
   出典はリデザイン時の申し送り文書
   `docs/legacy-ui-handover/spec-amendment-frontend-redesign.md:113-114`
   「フォーム最大幅 450px / **フォームレスポンシブ幅 `calc(100vw - 48px)`**」で、
   これはデザインモックの数値であり、**WordPress テーマの中に置かれる前提が入っていない**（§4）。
3. **`100vw − 48px` は、現行の構造では原理的に満たせない。** テーマのグローバルパディングは
   プラグインが制御できない領域で、Twenty Twenty-Five では `clamp(30px, 5vw, 50px)`＝
   **ビューポート幅によって 30〜50px の間で変わる**（§3）。テーマを変えれば別の値になる。
   ＝ **ビューポート相対の期待値は、テーマ非依存には書けない**。
4. 付随して、**死んでいる CSS ルールを1つ発見**した。`@media (max-width: 480px)` の
   `.smb-front-root { padding: 12px }`（`frontend.css:1247`）は、後続の
   `@media (max-width: 768px)` の `{ padding: 15px }`（`frontend.css:2774`）に**同特異度・後勝ちで打ち消されている**。
   375px で効いているのは 15px のほう（実測）。**どちらが意図かは未確認**（§6）。
5. したがって決めるべきは「285px を直すか」ではなく、**「①テストの期待式を実装準拠に書き換えるか、
   ②プラグイン側の余白設計を変えるか、③両方そのままで起票をクローズするか」**（§5）。

## 2. 実測（ブラウザの箱モデル・wp-env / Twenty Twenty-Five 1.5 / WP 7.1）

`http://localhost:8888/?page_id=5`（`[smart_booking]` を貼った固定ページ）で、
`.smb-front-main-page` から祖先をたどって計測した。

### viewport 375px（テストが失敗する条件）

| 要素 | width | padding L/R | max-width |
|---|---|---|---|
| `body` / `.wp-site-blocks` | 375 | 0 | none |
| `main.wp-block-group has-global-padding` | 375 | **30 / 30** | none |
| `.entry-content.alignfull` | 375 | 30 / 30（margin −30） | none |
| `.smb-front-root` | **315** | **15 / 15** | 720 |
| `.smb-front-step`（= `.smb-front-main-page` の器） | **285** | 0 | — |

`375 − 60（テーマ）− 30（プラグイン）= 285`。**テストの期待値 327 との差 42px は、
テーマのグローバルパディング 30px×2 のうち、テストが見込んでいた 24px×2 を超える分**
（60 − 48 = 12px）と、**プラグイン自身の 15px×2 = 30px** の合計。

### viewport 1280px（テストが成功する条件）

`.smb-front-main-page` は `max-width: 450px` に当たるため 450px。テーマ余白（この幅では 50px×2）も
`.smb-front-root`（max-width 720 + padding 16）も、450 より広いので効かない。
＝ **desktop 側の assert が通るのは「max-width が支配的だから」であって、余白計算が一致しているからではない。**

## 3. 実装の意図（プラグイン側 CSS）

| ルール | 値 | 位置 |
|---|---|---|
| `.smb-front-root` | `max-width: 720px; margin: 0 auto; padding: 16px` | `frontend.css:95` |
| `.smb-front-root`（≤768px） | `padding: 15px` | `frontend.css:2774`（**375px で効いているのはこれ**） |
| `.smb-front-root`（≤480px） | `padding: 12px` | `frontend.css:1247`（**後続ルールに打ち消され死んでいる**） |
| `.smb-front-main-page` / `-confirm-page` / `-done-page` | `max-width: 450px; width: 100%; margin: 0 auto` | `frontend.css:1656-1662` |

- プラグインは **「テーマのコンテンツ幅の中で、最大 450px・左右 15px の余白」** という設計になっている。
  これは「テーマの中に置かれるブロック」としては自然な作り（テーマの余白を尊重し、外へはみ出さない）。
- リデザイン仕様の mobile 節（`spec-amendment-frontend-redesign.md:209`）にも
  **「フォーム padding 15px」** とあり、**現行の 15px はこの記述と一致している**。
  ＝ **プラグイン側の余白は仕様どおり**で、食い違っているのは「フォーム全体の幅」の数式だけ。

### テーマ側の余白（プラグインの制御外）

Twenty Twenty-Five のグローバルパディングは spacing size `50` = **`clamp(30px, 5vw, 50px)`**
（`wp_get_global_settings()` で実測）。375px では 30px、1280px では 50px に解決する。
**テーマ／ユーザーのテンプレート設定で変わる値**であり、プラグインからは動かせない
（動かすなら `alignfull` 相当の打ち消しが必要で、それはテーマのレイアウトと戦うことになる）。

### `calc(100vw - 48px)` は宣言として一度も実装されていない（重要）

`src/` 全文検索で `100vw` は **2 箇所ヒットするが、どちらもコメント**であり、CSS 宣言は存在しない。

| 位置 | 内容 | 読み取れること |
|---|---|---|
| `frontend.css:1647-1662`（Gen-A） | 「仕様 …「変更2: レイアウト」のフォーム最大幅 450px / **`calc(100vw - 48px)`** を … 適用する」と書いたうえで、実装は `max-width: 450px; width: 100%; margin: 0 auto` | **実装者はモックの数式を「コンテナ幅いっぱい（`width: 100%`）」と読み替えて実装した**。＝ 余白は器（テーマ＋`.smb-front-root`）に任せる、という設計判断が当時からあった |

＝ **モバイル側の数式は実装されたことが無く、テストだけがそれを要件として持っている。**

## 5. 判断の選択肢（決めるのは人間）

| 案 | 内容 | 長所 | 短所・リスク |
|---|---|---|---|
| **案A: テストの期待式を実装準拠にする** | mobile 側を「viewport より狭く、`.smb-front-root` の内側に収まっていること」など**構造的な性質**に書き換える（例: `width === root の content width` かつ `<= 450`） | テーマ非依存になり、テーマ差でも壊れない。プラグインの利用者向け表示は1ピクセルも変わらない | 「フォームレスポンシブ幅 `100vw − 48px`」という申し送り文書の記述は**満たさないまま**になる（文書側の追記が要る） |
| 案B: プラグイン側で余白を詰める | `.smb-front-root` の ≤768px パディングを 15px → 12px（死んでいる ≤480px ルールを生かす等）にする | 数 px だけ広くなる | **327px には届かない**（テーマの 60px が残るため、12px にしても 291px）。＝ テストは赤のまま。**全ユーザーのフロント表示が動く割に、目的を達成しない** |
| 案C: テーマの余白を打ち消して全幅化 | ラッパーに negative margin / `alignfull` 相当を当て、`100vw − 48px` を実現する | 申し送り文書の数値どおりになる | **テーマのレイアウトと戦う**。テーマ・ページテンプレート・他ブロックとの相性で崩れる恐れ。ユーザーの既存サイトの見た目を大きく変える。**リスクが最も高い** |
| 案D: 現状維持でクローズ | 実装もテストも変えず、起票に「実装が正・テストが陳腐化」と記録して閉じる | コスト 0 | **赤が1件残り続ける**（回帰ゲートのベースライン既存赤として毎回仕分けが必要） |

> 所見（判断ではない）: §2〜§4 の事実からは **案A が最も筋が通る**。理由は
> ①実測 285px はプラグイン側 CSS の設計（15px 余白）と申し送り文書の mobile 節（padding 15px）に
> **一致している**、②期待値 327px を満たすにはテーマの余白を打ち消すしかなく、それは
> 「テーマの中で行儀よく収まる」という現在の設計判断を覆す、③desktop 側の 450px assert は
> そのまま残せる。ただし**案Aを採るなら、申し送り文書側にも「レスポンシブ幅はテーマの
> コンテンツ幅に従う」と追記して食い違いを消す**必要がある。

## 6. 付随して見つかった件（別途の判断が要る）

**`.smb-front-root` の ≤480px パディング 12px が死んでいる。**

```
frontend.css:1247  @media (max-width: 480px) { .smb-front-root { padding: 12px } }   ← 177ba69 Phase 3 Gen-D（§8.2 で訂正）
frontend.css:2774  @media (max-width: 768px) { .smb-front-root { padding: 15px } }   ← 後から追加・後勝ち
```

同特異度で後ろに書かれた 768px 側が勝つため、**480px 以下でも 15px** になっている（実測）。
スマホで 12px にしたかったのか、15px に統一したかったのかは**コミット履歴からは断定できない**（§8.2 に材料を追記）。
案A（テスト側を直す）を採る場合でも、この重複は残る。**どちらを残すかは設計判断**。

## 8. 追記（2026-09-12・判断後）

### 8.1 §5 の判断は確定した

**人間判断で案A（テストの期待式を構造的な性質へ書き換える）を採用。**
実施内容・新しい期待式・回帰ゲート結果は
`docs/bugs/phase9-form-width-mobile-285px.md`（**クローズ済み**）が正本。
出荷コード（CSS）は無変更。

同じ誤記由来の赤が **もう 1 本** あった（本レポート作成時には把握していなかった）:

- `tests/e2e/phase9-redesign-confirm-responsive.spec.js:220`
  「レスポンシブ 375px: フォーム幅 327px + 横スクロール無し」。
  `page.setViewportSize( { width: 375 } )` で自前に切り替えるため **desktop / mobile 両プロジェクトで赤**。
  さらに同 spec は `mode: 'serial'` のため、この赤が後続 2 本（×2 プロジェクト = 4 テスト）を
  **did-not-run** にしていた。v0.5.3〜v0.5.6 の回帰ゲートはこの spec を絞り込み対象に含めていなかったため
  記録に現れていなかった。**案A と同じ書き換えで解消済み。**

### 8.2 §6（死んでいる `padding: 12px`）の判断材料 — git 履歴を追加

**今回は削除も変更もしていない（判断保留）。** 以下は決めるために必要な材料。

#### ⚠️ §6 の帰属を訂正

§6 で 12px 側を「Gen-C で追加済み」と書いたが、**実際は `177ba69`「Phase 3 Gen-D: カラーCSS変数完全反映 + レスポンシブ + a11y」（2026-04-25）**。
「Gen-C で追加済み」という表現は `frontend.css:2769` の**コメントの記述**を引き写したもので、
コミット履歴と一致しない（`frontend.css:2767` の `calc(100vw - 48px)` 誤記と同じコメントブロック）。

#### 2 つのルールの出自

| | ルール | 追加コミット | 日付 | 依拠した仕様 |
|---|---|---|---|---|
| 先（負け） | `@media (max-width: 480px) { .smb-front-root { padding: 12px } }`（`frontend.css:1247`） | `177ba69` Phase 3 Gen-D | 2026-04-25 | **リデザイン前**。同ブロックのコメント（`frontend.css:1242`）に「`.smb-front-root` の横パディングを少し詰める」と**明示的な意図**がある |
| 後（勝ち） | `@media (max-width: 768px) { .smb-front-root { padding: 15px } }`（`frontend.css:2774`） | `cce3093` Gen-D「確認画面/完了画面/レスポンシブ/アニメーションのUI刷新」 | 2026-04-27 | **リデザイン仕様**「変更5: レスポンシブ / タブレット（≤768px）」の**「フォーム padding 15px」** |

同特異度・同メディア条件の重なりで、**後に書かれた 15px が ≤480px でも勝つ**（実測 15px）。

#### 判断材料として読み取れること

1. **リデザイン仕様（新しい側）はスマホ（≤480px）のルート余白に言及していない。**
   「変更5: レスポンシブ」の `スマホ（≤480px）` 節の項目は
   **日付カード / 時間スロット / 月表示ヘッダー**のみで、**フォーム padding は `タブレット（≤768px）` 節にしかない**
   （`spec-amendment-frontend-redesign.md`「変更5」実測）。
   ＝ **仕様の読みとしては「≤768px 以下は一律 15px」が素直**。12px は**リデザイン前の意図の残骸**と読める。
2. ただし 12px 側には「少し詰める」という**明示的な意図コメントが残っている**ため、
   「スマホでは 12px にしたかったが、後の一括指定に気づかず潰された」という読みも**履歴からは否定できない**。
   `cce3093` のコミットメッセージ・差分に「12px を 15px に統一する」旨の記述は無い（＝**意図的な上書きの証跡は無い**）。
3. **どちらを残しても 327px には届かない**（§5 案B）。＝ **本件（幅のテスト）とは無関係の独立した判断**。
4. **実害は現状ゼロ**。見た目は 15px で一貫しており、壊れている箇所は無い。
   残すコストは「読んだ人が 12px が効いていると誤解する」ことだけ。

#### 結論（材料の要約）

- **「どちらが意図か」はコミット履歴だけでは断定できない**（上記 2）。
- ただし **仕様文書の構造（上記 1）からは 15px 一律が整合的**で、12px 側が取り残されたと読むのが自然。
- 取りうる対応は ①12px ルールを削除して 15px 一律を明示（表示は不変）／
  ②12px を活かすため ≤480px 側を `@media (max-width: 768px)` ブロックより**後ろ**へ移す（**全ユーザーのスマホ表示が 3px 動く**）。
- **①は表示不変・②は表示変化**。出荷コードに触るため、いずれも `frontend.css` を触る次のリリースで
  §8.1 の残課題（`frontend.css:2767` のコメント誤記）と**まとめて**扱うのが筋。
